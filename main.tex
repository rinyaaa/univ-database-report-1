\begin{abstract}
本稿では，Next.js と Djangoを組み合わせたWebベース在庫管理システムの設計仕様を報告する．
本システムは，商品の登録・在庫数の管理・売上の一括登録・月別集計をブラウザ上で実現するものである．
設計において特に考慮した点は，JWT をhttpOnly Cookieで管理することによるセキュアな認証設計，
自己参照外部キーを用いたカテゴリ階層の柔軟な表現，
およびCSV一括登録における同期・非同期2方式の使い分けである．
本稿ではシステム要件，機能設計，データベース設計，API設計，実装の各観点からこれらの設計判断とその根拠を述べる．
\end{abstract}

\section{序論}
%===================================================

本稿で報告するシステムは，フロントエンドにNext.js，バックエンドにDjangoを採用した
SPA（Single Page Application）構成の在庫管理Webアプリケーションである．
設計上の主な課題として，(1) ステートレスなREST APIに適した認証方式の選択，
(2) 将来的な拡張を考慮したカテゴリ階層の表現，
(3) 大量データを対象とした売上一括登録での処理方式の選択，
の3点があった．
本稿では，これら3点の設計判断とその根拠を中心に，システム全体の設計仕様を述べる．

%===================================================
\section{機能設計}
%===================================================

\subsection{認証機能}

認証には JWT\cite{rfc7519} を用いた設計を採用した．
REST APIとの組み合わせで一般的に使われるセッション方式と比較すると，
JWTはサーバ側にセッション情報を保持しないステートレスな設計であるため，
水平スケールアウト時にセッション共有の仕組みを別途用意する必要がない点が利点である．

JWTの保管場所として，本設計ではhttpOnly Cookieを採用した．
LocalStorageはJavaScriptから自由に読み取れるためXSS攻撃によるトークン漏洩リスクがある\cite{owasp-session}のに対し，
httpOnly Cookieはブラウザがリクエスト時に自動付与し，JavaScriptからアクセスできないためXSS耐性が高い．
アクセストークンの有効期限は15分，Cookieの保持期間は12時間を設計値とした．

ただし，本実装ではフロントエンドとバックエンド間の認証フローに未解決の不具合が存在し，
ログイン後のAPI呼び出しが正常に通過できない状態である．
そのため現状の動作確認環境では，\texttt{REST\_FRAMEWORK}の
\texttt{DEFAULT\_AUTHENTICATION\_CLASSES}を空タプル，
\texttt{DEFAULT\_PERMISSION\_CLASSES}を空リストに設定して認証を無効化している．
認証機能の完全な実装は今後の課題である（\ref{sec:conclusion}節参照）．

\subsection{商品管理機能}

商品情報の登録・一覧・編集・削除（CRUD）を提供する．
商品には名称・単価・説明・カテゴリを設定でき，
商品IDは自動採番とする．
商品名と単価は必須項目とし，単価は1〜99,999,999円の範囲での入力を求める．
入力値の検証はフロントエンドの\texttt{react-hook-form}\cite{react-hook-form}による
フォームバリデーションと，バックエンドのDRFシリアライザによるバリデーションの2層で行う．

\subsection{在庫管理機能}

商品ごとに仕入れ（在庫増加）と卸し（在庫減少）を記録する．
卸し登録時には，現在の在庫数（仕入れ合計$-$売上合計）が
卸し要求数量を下回る場合に操作を拒否し，
在庫数がゼロを下回ることを防止する制約をアプリケーション層で実装する（詳細は\ref{sec:impl}節）．

\subsection{CSV一括売上登録機能}

大量の売上データをCSVファイルで一括登録する機能である．
CSVには商品ID(\texttt{product})，日付(\texttt{date})，数量(\texttt{quantity})の
3フィールドが必要である．
同期処理と非同期処理の2方式を提供しており，
データ量や用途に応じてユーザが選択できる設計とした（詳細は\ref{sec:csv}節）．

\subsection{売上集計機能}

登録された売上データを月単位で集計し，月別の売上合計数量を一覧表示する．
集計はDjango ORMの\texttt{TruncMonth}と\texttt{Sum}を組み合わせてSQL集計として実装し，
アプリケーション側での集計処理を排除することでパフォーマンスを確保している．

\subsection{テーブル構成とER概要}

本システムのデータベースにはMySQL 8\cite{mysql-docs}を採用した．
リレーショナルデータベースを選択した理由は，在庫数の計算が複数テーブルの
集計クエリに依存しており，JOIN・UNION・GROUP BYといったSQL操作の
表現力が必要であることに加え，トランザクション保証（ACID）が
在庫整合性の維持に不可欠であるためである．

テーブル構成はcategory・product・purchase・sales・sales\_fileの5テーブルであり，
以下の各節でスキーマと設計根拠を述べる．

\subsection{認証APIの設計}

認証APIはコードとして実装されているが，前述の通り現在は無効化されている．
以下は設計意図の記録である．

ログインAPIはリクエストボディのユーザ名・パスワードを
\texttt{TokenObtainPairSerializer}で検証し，
アクセストークンとリフレッシュトークンの両方を
httpOnly Cookieにセットして応答する設計である\cite{simple-jwt}．
一般的なJWT実装がAuthorizationヘッダを使うのに対し，
\texttt{AccessJWTAuthentication}クラスをカスタム実装して
CookieからトークンをHTTPヘッダへ移し替える処理を加えることで，
フロントエンド側のトークン管理コードを不要にし，XSS耐性を高める意図がある\cite{owasp-session}．

リトライAPIは期限切れのアクセストークンをリフレッシュトークンで更新し，
新しいトークンペアをCookieに保存して応答する設計である．
図\ref{fig:auth-flow}に設計上の認証フローを示す．

なお，ログアウトAPIはバックエンドでCookieを削除する実装となっているが，
現在のフロントエンド実装（\texttt{layout.tsx}）では
ログアウトボタンクリック時にAPIを呼び出さず，
\texttt{router.replace("/login")}によるページ遷移のみを行っている．
そのため現状ではログアウト後もCookieが残存する状態であり，
ログアウトAPIの呼び出しを追加することが今後の課題である．

\subsection{商品APIの設計}

商品APIは\texttt{/api/inventory/products/}にGET・POST・PUT・DELETEを実装し，
Djangoの\texttt{APIView}を継承した\texttt{ProductView}クラスとして定義した．
本システムでは標準的なCRUD操作を\texttt{ModelViewSet}\cite{drf-docs}で
自動生成する実装も合わせて用意しているが，
バリデーションやエラーレスポンスの細かな制御が必要な場合に
\texttt{APIView}による手動実装が有効であると考える．

\subsection{在庫履歴APIの設計}
\label{sec:union}

在庫履歴APIは，仕入れテーブルと売上テーブルのレコードを統合して返す．
2つのテーブルを統合するため，ORMのUNION操作を活用した設計とした．
仕入れクエリには\texttt{type=Value('1')}，売上クエリには\texttt{type=Value('2')}を
付与することでレコードの種別を識別可能にし，日時順に並べて応答する．
この設計によりフロントエンドは単一のAPIからすべての在庫変動履歴を取得でき，
表示ロジックをシンプルに保てる．

\subsection{仕入れ・売上APIの設計}

仕入れ登録APIは商品ごとの仕入れ数を登録するためのエンドポイントである．
エンドポイントは\texttt{/api/inventory/purchases/}であり，POSTメソッドのみを受け取る．
リクエストボディには商品ID・数量・仕入れ日時を含むJSONオブジェクトを送信する．
\texttt{PurchaseSerializer}を使用してリクエストデータを検証し，
検証に成功した場合は仕入れ情報を登録してHTTPステータスコード201 Createdを返す．

売上登録APIは商品ごとの卸し数を登録するためのエンドポイントである．
エンドポイントは\texttt{/api/inventory/sales/}であり，POSTメソッドのみを受け取る．
登録時には在庫整合性チェックを行い，
卸し数量が現在の在庫数を超える場合は\texttt{BusinessException}でエラーを返す
（詳細は\ref{sec:impl}節）．
検証に成功した場合はHTTPステータスコード201 Createdを返す．

\subsection{CSV一括登録APIの設計}

CSV一括登録APIはCSVファイルをアップロードして売上データを一括登録するためのエンドポイントである．
同期処理のエンドポイントは\texttt{/api/inventory/sync/}，
非同期処理のエンドポイントは\texttt{/api/inventory/async/}であり，
いずれもPOSTメソッドのみを受け取る．
リクエストボディにはCSVファイルを含むマルチパートフォームデータを送信する．
CSVファイルには\texttt{product}・\texttt{date}・\texttt{quantity}の3フィールドが必要である．
2方式の設計詳細は\ref{sec:csv}節で述べる．

\subsection{売上集計APIの設計}

売上集計APIは月別の売上数を集計して返すためのエンドポイントである．
エンドポイントは\texttt{/api/inventory/summary/}であり，GETメソッドのみを受け取る．
Django ORMの\texttt{TruncMonth}と\texttt{Sum}を組み合わせ，
月別に集計した売上数をJSON形式でレスポンスとして返す．
リクエストボディは不要であり，集計結果は年月と売上数量のペアで返す．

\subsection{環境構築}

開発環境はVS Code Dev Container\cite{devcontainer-vscode}とDocker Compose\cite{docker-compose-docs}を組み合わせて構築した．
Docker Composeはデータベース（MySQL）コンテナのみを管理し，
フロントエンドとバックエンドはそれぞれ独立したDev Container上で実行する構成とした．

この構成を選んだ理由は，フロントエンド・バックエンドのホットリロードを
Docker内で実行するよりもDev Container（ホストマシン寄りの環境）で行う方が
ファイル変更の検知が速く，開発時の体験が向上するためである．
一方，DBはデータの永続化が必要なためコンテナ化が適切と判断した．

データベースコンテナはdocker image \texttt{mysql:8}を使用し，
ポート53306で公開する．
環境変数\texttt{MYSQL\_ROOT\_PASSWORD}でルートパスワードを，
\texttt{TZ}でタイムゾーンをAsia/Tokyoに設定する．

バックエンドのDev ContainerはMicrosoftが提供するDev Container用イメージ
（\url{mcr.microsoft.com/devcontainers/python:1-3.11-bullseye}）を使用する．
Djangoのプロジェクト構成は，settings.pyを環境別（\texttt{base.py}・\texttt{development.py}等）に
分割する構成とした．
環境間で共通の設定は\texttt{base.py}に記述し，
開発環境固有のDB接続情報等は\texttt{development.py}で上書きする．
サーバ起動時に\texttt{--settings config.settings.development}を指定することで
開発用設定を読み込む．

フロントエンドのDev ContainerはDocker image \texttt{node:18}を使用する．
バックエンドへのAPIリクエストは，Next.jsのRewrites機能\cite{nextjs-rewrites}を用いて
\texttt{/api/:path*}を\texttt{http://host.docker.internal:8000/api/:path*/}に転送する設定を行った．
この構成によりフロントエンドとバックエンドのオリジンが同一になるため，
CORSエラーを回避できる．

\subsection{在庫整合性チェックの実装}
\label{sec:impl}

卸し登録時の在庫整合性チェックは，
仕入れ合計と売上合計をそれぞれSQLの\texttt{SUM}集計で取得し，
式\eqref{eq:stock}を満たさない場合に\texttt{BusinessException}を送出して操作を拒否する実装とした．

\begin{equation}
  \sum \textit{purchase.quantity}
  \;\geq\;
  \sum \textit{sales.quantity} + \textit{new\_quantity}
  \label{eq:stock}
\end{equation}

集計時には\texttt{Coalesce(Sum('quantity'), 0)}を使用する．
\texttt{Coalesce}でNULLを0に変換することで，
仕入れや売上がまだ1件も存在しない商品に対しても
NullPointerExceptionなく正しく動作する．
なお，現在の実装では複数の同時リクエストが競合した場合に
チェックをすり抜ける可能性があり，今後の課題として残る（\ref{sec:conclusion}節参照）．

完了後に\texttt{status=ASYNC\_PROCESSED}へ更新する．
この際，\texttt{select\_for\_update()}を用いて処理対象レコードに対して
行レベルロックを取得することで，
バッチプロセスが複数起動された場合の二重処理を防止している\cite{mysql-docs}．
さらに\texttt{@transaction.atomic}デコレータによってトランザクション管理を行い，

\subsection{フロントエンド実装}

\subsubsection{ディレクトリ構成}

フロントエンドはNext.jsのApp Router\cite{nextjs-approuter}を用いて実装した．
App Routerではファイルベースのルーティングを採用しており，
\texttt{app/}ディレクトリ以下のディレクトリ構造がそのままURLパスになる．
\texttt{layout.tsx}ファイルにはその階層以下のページ共通レイアウトを定義でき，
\texttt{page.tsx}ファイルには各ページのコンテンツを定義する．
\texttt{[id]}のような動的ルートで商品IDに応じた在庫管理ページを実現している．

\subsubsection{フェッチャーの実装}

APIとの通信は\texttt{plugins/axios.ts}に実装したフェッチャーを通じて行う．
\texttt{axios}\cite{axios-docs}の\texttt{axios.create()}でインスタンスを作成し，
\texttt{Content-Type: application/json}をヘッダに設定してJSON形式でリクエストを送信する．
レスポンスインターセプターでは成功時にはそのままレスポンスを返し，
401エラー検知時はリトライAPIを呼び出して新しいトークンを取得し元のリクエストを再送する設計とした．
これにより，認証ロジックをアプリケーション全体の一箇所に集約できている．

\subsubsection{商品一覧画面}

商品一覧画面は\texttt{app/inventory/products/page.tsx}に実装する．
\texttt{useEffect}フックを使用して初期レンダリング時にフェッチャーで商品情報を取得し，
Material UI\cite{mui-docs}の\texttt{TableContainer}コンポーネントで表形式に表示する．
\texttt{useState}フックで「現在編集中の商品ID」を管理することで，
同時に1件だけ編集状態にある制御を実現している．
入力値の検証は\texttt{react-hook-form}\cite{react-hook-form}の\texttt{register}で行い，
エラーメッセージをテキストエリア下部に表示する設計とした．

\subsubsection{在庫管理画面}

在庫管理画面は\texttt{app/inventory/products/[id]/page.tsx}に実装する．
Next.jsのApp Routerでは動的ルートのパラメータはコンポーネントの\texttt{params}プロパティとして渡されるため，
\texttt{params.id}で商品IDを取得する．\texttt{useEffect}フックで
初期レンダリング時に商品情報と在庫履歴を取得する．
画面上部の仕入れ・卸しフォームには数量入力欄と操作ボタンを配置し，
\texttt{react-hook-form}でバリデーションを行う．
画面下部には在庫履歴をテーブル形式で最新順に表示する．

\subsubsection{売上一括登録画面}

売上一括登録画面は\texttt{app/inventory/import\_sales/page.tsx}に実装する．
\texttt{useEffect}フックで月別売上集計を初期取得し，\texttt{TableContainer}で表示する．
Material UIの\texttt{MuiFileInput}コンポーネントでファイル選択エリアを実装し，
同期・非同期それぞれの登録ボタンと組み合わせてフォームを構成する．
登録ボタンクリック時にフェッチャーでCSV一括登録APIへリクエストを送信する設計とした．

%===================================================
\section{まとめ}
\label{sec:conclusion}
%===================================================

本稿では，Next.jsとDjangoを用いた在庫管理Webアプリケーションの
設計仕様を報告した．
序論で挙げた3点の設計課題に対する本システムの対応は以下の通りである．

認証設計としてJWTをhttpOnly Cookieで管理する方式を採用し，
XSSに対してLocalStorage保管より高い耐性を持つ設計とした．
しかし現状ではフロントエンドとの認証連携に未解決の不具合があり，
認証機能を無効化した状態で動作している．
認証フローの不具合解消が最優先の課題であり，
その後，発行済みトークンの即時無効化（トークンブラックリスト）への対応も必要となる．

自己参照外部キーによるカテゴリ階層は，
固定深さのテーブル分割案と比較してシンプルな実装で可変深さを表現できた．
ただし，循環参照（あるカテゴリが自身の子孫カテゴリを親に指定する）を
防ぐ制約が現状では未実装であり，アプリケーション層での対策が必要である．

CSV一括登録の同期・非同期2方式は，
少量データから大量データまで対応できる柔軟な設計を実現した．
\texttt{select\_for\_update}を用いたロック取得で二重処理を防止しているが，
処理完了をユーザに通知する仕組みが未実装であり，
WebSocketまたはServer-Sent Eventsを用いた通知機構の追加が今後の課題である．

また，在庫整合性チェックはアプリケーション層のみで行っており，
並行リクエストによるチェックのすり抜けリスクが残る．
MySQLのトランザクション分離レベルとロック機構を活用したDBレベルでの保証が
より堅牢な解決策となるが，本実装ではその対応は今後の課題として残した．
